# Anforderungsmanagement

> Standard für die Anforderungsdokumentation aller Teams im Modul 5CS-SOPR-50.

Damit alle Produktteile des gemeinsamen Projekts zusammenpassen und
nachvollziehbar bleiben, dokumentieren alle Teams ihre Anforderungen einheitlich
im Git-Repository.

Dieser Standard basiert auf den Vorgaben unserer Betreuerin und unterstützt
die Querschnittsaufgabe "Requirements and Integration" (RI), welche vom
Orga-Team koordiniert wird.

## 1. Grundprinzip: Vier Ebenen sauber trennen

Um Missverständnisse und verfrühte Lösungsfestlegungen zu vermeiden, müssen vier
Begriffe strikt getrennt werden:

| Ebene | Frage | Beschreibung | Beispiel |
| :--- | :--- | :--- | :--- |
| **1. Idee** | Könnte das für das Produkt interessant sein? | Ein initialer Gedanke oder Vorschlag. Muss noch nicht vollständig, eindeutig oder prüfbar sein. | "Wir könnten ein Quest-System einbauen." |
| **2. Use Case (UC)** | Was möchte wer mit dem Produkt tun? | Beschreibt das Ziel eines Akteurs aus Nutzersicht und den Ablauf der Interaktion. | "Der Spieler nimmt bei einem NPC eine Quest an." |
| **3. Anforderung** | Was muss das Produkt konkret leisten? | Präzise, prüfbare Vorgabe mit Akzeptanzkriterien und Referenz auf ein GitHub-Issue. | "Das Quest-System muss dem Spieler ermöglichen, eine verfügbare Quest bei einem NPC anzunehmen." |
| **4. Lösung** | Wie wird die Anforderung technisch umgesetzt? | Konkrete technische Umsetzung (Mod, Skript, Plugin, Konfiguration). | "Wir nutzen Mod A und konfigurieren Quests über JSON-Dateien." |

:::warning Wichtig
Anforderungen beschreiben das **WAS** (fachlicher Bedarf), nicht das **WIE**
(technische Lösung). Die technische Lösung kann sich ändern, während die
Anforderung bestehen bleibt.
:::

## 2. Element-Kennungen: TEAM#Issue-ID

Wir nutzen **keine Typ-Kürzel** (wie `FR-`, `NFR-`, `UC-`, `IF-`, `CR-`),
sondern referenzieren ausnahmslos jedes Element über das einheitliche Schema:

```text
TEAM#Issue-ID
```

Beispiele:
- `orga#4` (Infrastruktur / Server-Setup)
- `assets#10` (Asset-Request oder Modellierung)
- `builder#12` (Gebäude-Abschnitt)
- `coding#15` (Interaktionslogik oder Skript)
- `story#24` (Handlungsstrang oder Quest)
- `recherche#23` (Studiengangsinformationen)

### Vorteile
- Keine künstlichen, parallelen Nummernkreise.
- Eindeutige Traceability zwischen Dokumentation, Git-Commits, Pull Requests und
  dem GitHub Project Board.
- Direkte Verknüpfung mit den Verantwortlichen und Diskussionen im Issue.

## 3. Typisierung von Anforderungen

Im GitHub-Issue oder in den Tabellenspalten kann zur fachlichen Einordnung der
Typ vermerkt werden (jedoch ohne Auswirkung auf die Kennung):

- **Funktional:** Konkretes Systemverhalten oder Aktion (z. B. "Der Server
  speichert den Fortschritt alle 5 Minuten").
- **Nichtfunktional:** Qualitätseigenschaften (z. B. Ladezeit unter 3 Sekunden,
  intuitive Bedienbarkeit).
- **Randbedingung:** Gesetzte Rahmenbedingungen (z. B. Minecraft Bedrock
  Version 1.21.x, Lizenzen).
- **Schnittstelle:** Vereinbarte Daten- oder Leistungsübergaben zwischen zwei
  Teams.

## 4. Priorisierung

Die Priorisierung erfolgt einheitlich nach der vierstufigen Skala des GitHub
Project Boards:

| Priorität | Bedeutung | Verwendung |
| :--- | :--- | :--- |
| `Urgent` | Kritischer Blocker | Sofortige Bearbeitung erforderlich; blockiert andere Teams oder den aktuellen Meilenstein. |
| `High` | Hohe Priorität | Kernfunktionalität für den aktuellen Sprint oder Meilenstein. |
| `Medium` | Mittlere Priorität | Wichtig für das Gesamtprodukt, aber nicht unmittelbar zeitkritisch. |
| `Low` | Niedrige Priorität | Nice-to-have, Verbesserung oder Detailaufgabe bei Restkapazitäten. |

## 5. Statusmodell und Lebenszyklus

Die Bearbeitung spiegelt sich im Status des GitHub-Issues auf dem Project Board
wider:

```text
[BACKLOG] -> [TODO] -> [IN PROGRESS] -> [DONE]
```

- **BACKLOG:** Vorgeschlagene Idee oder Anforderung, im Team oder mit
  Stakeholdern noch in Klärung.
- **TODO:** Fachlich abgestimmt, Akzeptanzkriterien definiert und für den
  aktuellen Sprint eingeplant.
- **IN PROGRESS:** Aktiv in Entwicklung / Bearbeitung.
- **DONE:** Fertig implementiert, getestet und gemäß teaminterner Definition of
  Done (DoD) abgenommen.

## 6. Qualitätskriterien für eine Anforderung

Eine saubere Anforderung erfüllt folgende Kriterien:

1. **Eindeutig referenzierbar:** Verknüpft mit `TEAM#Issue-ID`.
2. **Verständlich:** Präzise formuliert ohne teaminternen Fachjargon.
3. **Notwendig:** Es gibt eine klare Begründung (Zweck für das Gesamtprodukt).
4. **Prüfbar / Testbar:** Es existieren konkrete Akzeptanzkriterien. Frage:
   "Woran prüfen wir bei der Abnahme, ob die Anforderung erfüllt ist?"
5. **Lösungsneutral:** Gibt das gewünschte Verhalten vor, nicht die Codezeile
   oder das konkrete Mod-Detail.

## 7. Schnittstellenmanagement (Inter-Team)

Teams entwickeln Produktteile nicht isoliert. Sobald ein Team Daten, Assets oder
Funktionen eines anderen Teams benötigt, wird eine Schnittstellenvereinbarung
als Issue angelegt und dokumentiert.

### Pflichtfragen für jede Schnittstelle

- **Wer liefert?** (Anbieter-Team)
- **Wer benötigt?** (Nachfrager-Team)
- **Was wird geliefert?** (Gegenstand, z. B. 3D-Modell, Datentabelle,
  Event-Hook)
- **In welchem Format?** (Dateiformat, Namenskonvention, Koordinaten, Schema)
- **Bis wann?** (Fertigstellungstermin / Meilenstein)
- **Wer ist verantwortlich?** (Benannte Ansprechpersonen beider Teams)

Schnittstellen werden dem Orga-Team gemeldet, um das zentrale Interface-Register
aktuell zu halten. Vorlage: siehe
[Schnittstellenvereinbarung](../vorlagen/schnittstellenvereinbarung.mdx).

## 8. Regelmäßige Abgaben & Updates

Gemäß Vorlesungsvorgabe finden regelmäßige Abgaben statt:

1. **Wöchentliches Team-Update an RI:** Jedes Team pflegt wöchentlich seinen
   aktuellen Stand unter `statusberichte/<team>/` (Vorlage:
   [Wöchentliches Team-Update](../vorlagen/team-update.mdx)).
2. **Wöchentliches Gesamt-Update an die Betreuerin:** Das RI-Team (Orga)
   fasst alle Team-Stände zusammen und berichtet an die Betreuerin
   (Vorlage: [RI Wöchentliches Update](../vorlagen/ri-update.mdx)).
3. **Schnittstellenvereinbarungen & Change Requests:** Werden bei Bedarf
   ausgefüllt und im Git dokumentiert (Vorlagen:
   [Schnittstellenvereinbarung](../vorlagen/schnittstellenvereinbarung.mdx)
   und [Change Request](../vorlagen/change-request.mdx)).

Eine genaue Schritt-für-Schritt-Anleitung findest du in der
[Anleitung zum Ausfüllen der Dokumente](../vorlagen/anleitung.mdx).

## 9. Ablage und Struktur im Repository

Wir trennen strikt zwischen statischer Dokumentation und wöchentlichen
Statusberichten:

```text
docs/content/project/
|-- teams/<team-ordner>/            # Statische Dokumentation (bleibt bestehen)
|   |-- team-goals.mdx             # Aufgabenpaket, SDLC-Modell, Scopes
|   `-- anforderungen/             # Fortlaufender Anforderungsstand & Use Cases
`-- statusberichte/<team-ordner>/   # Dynamische Berichte (wöchentlich neu)
    |-- kw44.mdx                   # Wöchentliches Team-Update
    `-- ...
```
