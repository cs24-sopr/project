# Anleitung: GitHub Project Board

> Leitfaden zur Aufgaben- und Sprintverwaltung auf unserem zentralen Project Board.

Das zentrale Board für das gesamte Projekt ist unter folgendem Link erreichbar:

- **Board-Link:** [GitHub Project Board #3](https://github.com/orgs/cs24-sopr/projects/3)

Alle Teams arbeiten im selben Board. Getrennte Boards pro Team führen zu hohem Wartungsaufwand, Informationssilos und erschweren den teamübergreifenden Überblick.

## 1. Felder im Project Board

Jedes Issue wird über folgende Felder verwaltet:

| Feld | Bedeutung & Optionen |
| :--- | :--- |
| **Assigned Team** | Ordnet das Issue eindeutig einem Team zu (z. B. Orga, Builder, Interaktionsprogrammierung, Asset-Design, Recherche, Story-Design). |
| **Status** | Aktueller Bearbeitungsstand (siehe Workflow unten). |
| **Story Points** | Schätzung des relativen Aufwands für die Aufgabe (z. B. 1, 2, 3, 5, 8). |
| **Sprint** | Zugewiesener Sprint gemäß Namensschema `TEAMNAME-SPRINT-X` (z. B. `ORGA-SPRINT-1`). |

### Status-Workflow

```
[ BACKLOG ] --> [ TODO ] --> [ IN PROGRESS ] --> [ DONE ]
```

- **`BACKLOG`:** Noch nicht in einem aktiven Sprint zugeteilt. Dient als Sammelbecken für Anforderungen und Ideen.
- **`TODO`:** Für den anstehenden Sprint eingeplant und committet.
- **`IN PROGRESS`:** Das Issue wird aktiv bearbeitet und ist der ausführenden Person zugewiesen (Assignee).
- **`DONE`:** Die Aufgabe ist vollständig fertiggestellt, gereviewt und abgenommen.

## 2. Views und ihre Nutzung

Das Board bietet drei primäre Views für unterschiedliche Phasen der Sprintarbeit:

### View 1: "Backlog"

- **Inhalt:** Alle Issues sortiert nach ihrem Status.
- **Filter:** Über die linke Leiste kann das jeweilige Team gefiltert werden.
- **Zweck:** Pflege des Aufgabenpools, Schätzung von Story Points und Vorbereitung zukünftiger Arbeitspakete.

### View 2: "Planning"

- **Inhalt:** Alle Issues sortiert bzw. gruppiert nach ihrem zugewiesenen Sprint.
- **Filter:** Über die linke Leiste kann das jeweilige Team ausgewählt werden.
- **Zweck:** Schnelle Zuweisung von Issues zu Sprints während des Sprint Plannings sowie Kapazitätsübersicht über vergangene, aktuelle und kommende Sprints.

### View 3: "TEAM - Sprint"

- **Inhalt:** Alle aktiven Issues des laufenden Sprints.
- **Pflege:** Zu Beginn jedes neuen Sprints wird oben im Filter der aktuelle Sprintname aktualisiert (z. B. Filter von `ORGA-SPRINT-1` auf `ORGA-SPRINT-2` anpassen).
- **Zweck:** Tägliches Arbeitsboard für das Team zur Nachverfolgung des Sprintfortschritts.

## 3. Typischer Ablauf im Sprint-Zyklus

1. **Backlog befüllen & schätzen:**
   - Neues Issue erstellen.
   - `Assigned Team` setzen.
   - Story Points im Team besprechen und eintragen.
   - Status bleibt auf `BACKLOG`, das `Sprint`-Feld bleibt zunächst leer.

2. **Sprint Planning (View "Planning"):**
   - Das Team wählt im View "Planning" die Aufgaben für den nächsten Sprint aus.
   - Den ausgewählten Issues wird der neue Sprint zugewiesen (z. B. `BUILDER-SPRINT-1`).
   - Status der ausgewählten Issues von `BACKLOG` auf `TODO` setzen.

3. **Sprint-Durchführung (View "TEAM - Sprint"):**
   - Im View "TEAM - Sprint" den Filter auf den aktuellen Sprint anpassen.
   - Wer eine Aufgabe beginnt, weist sich als Assignee zu und schiebt das Issue auf `IN PROGRESS`.
   - Nach erfolgreichem Test, PR-Merge oder Abnahme wird das Issue auf `DONE` gesetzt.

4. **Sprint Review & Retro:**
   - Im Review werden die auf `DONE` stehenden Issues präsentiert.
   - Nicht fertiggestellte Issues verbleiben entweder im Backlog oder werden im nächsten Planning neu bewertet.
